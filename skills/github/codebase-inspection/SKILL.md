# Codebase Inspection with pygount

Analyze repositories for lines of code, language breakdown, file counts, and code-vs-comment ratios using `pygount`.

## When to Use

- User asks for LOC (lines of code) count
- User wants a language breakdown of a repo
- User asks about codebase size or composition
- User wants code-vs-comment ratios
- General "how big is this repo" questions
- User asks whether a codebase has unused/untracked junk to clean up before committing; see `references/unused-scratch-artifact-cleanup.md` for the conservative Git-first cleanup pattern
- User asks to clean unused code, remove dead/scratch artifacts, or check whether codebase changes have been committed
- User asks for a source-code tarball/archive of a repository, especially with current uncommitted source changes; use `references/source-tarball-export.md` for the safe manifest + sensitive-file verification pattern

## Prerequisites

```bash
pip install --break-system-packages pygount 2>/dev/null || pip install pygount
```

## 1. Basic Summary (Most Common)

Get a full language breakdown with file counts, code lines, and comment lines:

```bash
cd /path/to/repo
pygount --format=summary \
  --folders-to-skip=".git,node_modules,venv,.venv,__pycache__,.cache,dist,build,.next,.tox,.eggs,*.egg-info" \
  .
```

**IMPORTANT:** Always use `--folders-to-skip` to exclude dependency/build directories, otherwise pygount will crawl them and take a very long time or hang.

## 2. Common Folder Exclusions

Adjust based on the project type:

```bash
# Python projects
--folders-to-skip=".git,venv,.venv,__pycache__,.cache,dist,build,.tox,.eggs,.mypy_cache"

# JavaScript/TypeScript projects
--folders-to-skip=".git,node_modules,dist,build,.next,.cache,.turbo,coverage"

# General catch-all
--folders-to-skip=".git,node_modules,venv,.venv,__pycache__,.cache,dist,build,.next,.tox,vendor,third_party"
```

## 3. Filter by Specific Language

```bash
# Only count Python files
pygount --suffix=py --format=summary .

# Only count Python and YAML
pygount --suffix=py,yaml,yml --format=summary .
```

## 4. Detailed File-by-File Output

```bash
# Default format shows per-file breakdown
pygount --folders-to-skip=".git,node_modules,venv" .

# Sort by code lines (pipe through sort)
pygount --folders-to-skip=".git,node_modules,venv" . | sort -t$'\t' -k1 -nr | head -20
```

## 5. Output Formats

```bash
# Summary table (default recommendation)
pygount --format=summary .

# JSON output for programmatic use
pygount --format=json .

# Pipe-friendly: Language, file count, code, docs, empty, string
pygount --format=summary . 2>/dev/null
```

## 6. Interpreting Results

The summary table columns:
- **Language** — detected programming language
- **Files** — number of files of that language
- **Code** — lines of actual code (executable/declarative)
- **Comment** — lines that are comments or documentation
- **%** — percentage of total

## 7. Cleanup and Git Hygiene Workflow

When the user asks to clean unused code or asks whether work has been committed:

1. Start from repository truth:

```bash
git rev-parse --show-toplevel
git status --short
git log --oneline -5 --decorate
```

2. Classify untracked/modified files before deleting. Treat generated payloads, scratch probes, temporary downloads, caches, `.out` logs, and one-off task scripts as cleanup candidates. Keep production-looking scripts, tests, scheduled wrappers, docs, and skills unless clearly obsolete.

3. Prefer conservative cleanup:
   - Remove only untracked junk or files clearly generated by the current workflow.
   - Before deleting ignored scratch globs, prove they are not tracked with `git ls-files '<glob>'` and confirm the ignore rule with `git check-ignore -v <sample-file>`; this is especially useful for large batches like `tmp_*` probes.
   - Do not delete tracked files just because they look unused without searching references first.
   - Use `git grep` / repository search for candidate tracked files before removal.
   - If cleanup reveals a recurring junk pattern, patch `.gitignore` in the same pass so it does not accumulate again.

4. Verify after cleanup:
   - Run `git diff --check` before committing.
   - Run the smallest meaningful focused test suite for affected code.
   - If a test runner dependency is missing in the base environment, use a temporary `uvx --from ... --with ...` invocation rather than installing globally.

5. Commit and push when the user asks whether commits have been happening or implicitly asks for codebase maintenance to be finalized. Report exact commit hashes and final branch status.

6. When cleanup touches tracked operational JSON state such as Hermes cron job files, preserve existing object/job order and avoid formatter churn; see `references/operational-json-state-edits.md`.


Special pseudo-languages:
- `__empty__` — empty files
- `__binary__` — binary files (images, compiled, etc.)
- `__generated__` — auto-generated files (detected heuristically)
- `__duplicate__` — files with identical content
- `__unknown__` — unrecognized file types

## 7. Safe Cleanup of Unused / Scratch Artifacts

When the user asks to clean up unused code or repo junk, use a conservative git-backed workflow:

1. Start with `git status --short`, `git log --oneline -5`, and repo root discovery. Answer whether prior commits exist from real git output, not memory.
2. Classify untracked files before deleting. Good candidates: one-off probes, `tmp_*`, generated payload JSON, downloaded source dumps, browser scrape artifacts, `.out` logs, local backup directories, and cache-like directories. Do **not** delete tracked files or production-looking untracked scripts/tests without stronger evidence.
3. Prefer deleting only untracked scratch artifacts. If tracked code looks unused, first search references and inspect tests before removing it.
4. Update `.gitignore` with patterns for the removed generated artifacts so they do not return.
5. Verify with targeted tests or smoke checks relevant to the touched area. If dependencies are missing, use a temporary runner such as `uvx --from pytest --with <needed-package> pytest ...` rather than polluting the environment.
6. Commit the cleanup and push when the user asked whether commits are being made or expects repo hygiene to persist. Re-check `git status --short --branch` after pushing.

## Pitfalls

1. **Always exclude .git, node_modules, venv** — without `--folders-to-skip`, pygount will crawl everything and may take minutes or hang on large dependency trees.
2. **Markdown shows 0 code lines** — pygount classifies all Markdown content as comments, not code. This is expected behavior.
3. **JSON files show low code counts** — pygount may count JSON lines conservatively. For accurate JSON line counts, use `wc -l` directly.
4. **Large monorepos** — for very large repos, consider using `--suffix` to target specific languages rather than scanning everything.
5. **Do not confuse scratch cleanup with deleting dead tracked code** — untracked probes/payloads can often be removed directly, but tracked files need reference searches and tests before deletion.
6. **A clean working tree matters** — after maintenance, check `git status --short --branch`; if the user asked about committing, commit and push or clearly state why not.
7. **Operational JSON churn hides real changes** — for tracked scheduler/config state files, preserve original key/order layout and avoid committing incidental runtime timestamp/counter changes unless the repo policy expects a full live snapshot.
8. **Skill usage telemetry is usually noise** — loading/patching skills can touch `skills/.usage.json`; do not include that sidecar in unrelated cleanup commits.
9. **Do not archive the whole repo directory blindly** — for source exports, build a manifest from `git ls-files -co --exclude-standard`, then explicitly filter `.env`, local DBs, SQLite/state files, pyc/cache files, telemetry, and backup blobs before tar creation. Verify archive paths and checksum before sharing.
