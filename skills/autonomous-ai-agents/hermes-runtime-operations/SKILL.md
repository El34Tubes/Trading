# Hermes Runtime Operations

Use this skill when the user asks to validate what is working/not working in a live Hermes Agent install, install optional/system dependencies, or verify that a Hermes runtime feature works after setup changes.

This is an operations/checklist skill, not a replacement for the bundled `hermes-agent` reference skill. Load `hermes-agent` first for authoritative CLI/config commands, then use this skill for the practical validation workflow.

## Runtime Discovery Notes

- If a deterministic ops collector reports that `hermes doctor` hit its generic command timeout, rerun Doctor directly with a larger bounded timeout before treating it as broken. If the direct run succeeds, add a per-probe timeout override for Doctor rather than raising every collector timeout; then sync/compile all mirrored wrappers and prove the second autorepair run is silent. See `references/hermes-doctor-collector-timeout-2026-10-05.md`.
- When cleaning a repository that is also a live Hermes state directory, classify ignored runtime state separately from disposable scratch files, inspect cron/wrapper/open-file references, and use deterministic bounded snapshot retention; see `references/live-operations-repo-cleanup-and-snapshot-retention.md`.
- For a no-write audit of untracked paths before public publication, freeze the initial NUL-delimited Git manifest, hash duplicate root/profile copies, separate authored source from one-off probes and raw downloads, scan infrastructure identifiers and licensing as well as secrets, and recheck for concurrent staging/ignore changes before reporting; see `references/live-repository-untracked-publication-audit.md`.
- When a planner calls a missing stable `/root/.hermes/scripts/` helper but the canonical Wolfy implementation exists, add a thin delegating wrapper, preserve it through canonical autorepair and Mike/Clerky profile sync, then verify compile, executable mode, identical `--help`, and a silent second autorepair run; see `references/wolfy-coordination-cli-wrapper-preservation-2026-10-01.md`.
- For user questions about "crontab" on a Hermes host, check both the literal Linux crontab and Hermes's own scheduler; see `references/hermes-scheduler-vs-system-crontab-and-ttyd-browser.md`.
- For browser-visible hosted Hermes setups, look for a Traefik-routed `ttyd` container endpoint before assuming there is no browser UI; see `references/hermes-scheduler-vs-system-crontab-and-ttyd-browser.md`.
- For one-change config/cron self-modification under a periodic guardian, keep rollback anchored to the pre-change snapshot, prevent the guardian from promoting probationary hashes, and stage only the intentional schedule keys from a dirty live `jobs.json`; see `references/probationary-cron-self-modification.md`.
- For adjusted EOD ingest around stock splits, scan from each ticker's earliest stored bar, force full-history replacement only for unresolved split dates, persist exact completion markers, prove a zero-fetch second run, and close dirty-repo tasks with the authoritative `git rev-parse HEAD` hash; see `references/wolfy-split-safe-eod-ingest-and-verified-closure.md`.
- For budget-gated optimizer closure, **open `references/budget-gated-optimizer-closure.md` before any Phase-0/orientation tool call—not merely before creating or claiming the plan-only task**. This prerequisite still applies when the cron prompt already inlines or preloads the bundled `hermes-agent` skill: explicitly load this runtime-operations skill and its budget-closure reference before probing live state. Treat this as a hard ordering gate: if any live probe was started first, stop batching further orientation, load the reference, and restart the audit sequence with the dedicated budget decision probe; do not let earlier incidental output substitute for the canonical decision record. Skill/reference loading is a prerequisite because the first probe is state-sensitive: run `budget_gate.py --no-record` in its own small command, preserve its expected nonzero exit, and call the guardian only with documented flags (`--home /root/.hermes --skip-cli` for the cheap check). Do not first run bare `budget_gate.py` or probe guessed guardian flags with a fallback chain; the former writes orphan telemetry and the latter creates misleading error noise even if a retry passes. Check an expected-absent probation marker with a quiet existence probe (`test ! -e ...` or equivalent) rather than an unconditional file read, so healthy `no probation` state does not create spurious tool-error noise or pollute gateway diagnostics. The reference preflight also prevents recurring mistakes from guessed schema fields, `psql -v ... -c` interpolation, literal `%` characters in psycopg query strings, masked pytest discovery failures, and false stale-run alarms from the current scheduler-owned cron usage-sync row. **Before executing any ad-hoc psycopg KPI writer, inspect every SQL string containing `LIKE`/`ILIKE`: bind the wildcard as a parameter or escape literal percent signs as `%%`. Keep the insert and exact count/provenance assertions in one transaction. If the writer raises, first prove the current run still has zero metric rows, then repair and retry against the same task/run—never create a replacement closure merely because the first transaction failed closed.** Pytest-style suites must run under pytest with a nonzero collected-test assertion—`unittest` can exit 0 after collecting zero tests. Do not assume the newest heading in `optimization_todo.md` identifies the prior completed slice: reconcile Git `HEAD`, the linked `agent_tasks` row, and the latest terminal `agent_runs` row, then rerun that task's named DoD. Keep task DoD update, claim/run start, KPI insertion, commit metadata, and lifecycle completion as separately verified steps. Resolve stored test paths before running them and use fail-fast shells so a missing pytest target cannot be masked by later successful commands. Insert all current-run KPIs and their count/provenance assertions in one transaction so a scratch-query failure rolls back cleanly before retry; reuse the already-created task by fingerprint after a recoverable write failure rather than creating a duplicate. During final stale-run checks, require the task-linked inner run to be terminal but exclude only the exact fresh outer `cron:<current_job_id>` usage-sync row, which remains started until the current conversation exits. Treat the KPI insert as the audited decision-time snapshot: a final `budget_gate.py --no-record` probe can legitimately show a higher token total after concurrent cron/session-usage synchronization. Do not rewrite an already verified 25-row metric set after task/run closure merely to chase that moving total; report the stored decision-time value and the later final-probe value separately. Also run `git show --check <commit>` and `git show --name-only --format= <commit>` as separate commands—Git rejects combining `--check` with `--name-only`, and that command-line error must not be mistaken for a bad commit. If the guardian's latest cron result reports an auto-restore such as transient `optimizer_not_enabled` but an immediate production-home guardian probe passes, record the rollback (`config_rollbacks=1`) and preserve the exact snapshot/reason; do not erase it as stale noise or make a compensating orchestration edit during a budget-blocked run. Recheck the optimizer and guardian are enabled, cron list/status, gateway health, and probation state, then queue deterministic root-cause inspection for the next budget-healthy run.
- Historical Wolfy optimizer rows use several `task_type` spellings (`optimizer_plan_only`, `optimization_plan_only`, `optimization`, and `self_optimization`). Resolve the prior closure by exact `commit_hash = HEAD` first, then task ID or unique fingerprint; never let a narrow type filter silently select an older task. See `references/wolfy-optimizer-task-type-reconciliation.md`.
- When integration tests must temporarily use a live Postgres schema, replace normal psycopg connection-context semantics (which commit on successful exit) with an outer rollback-only connection; prove focused and repeated full suites leave the **complete write graph** unchanged, not merely strategy status or synthetic ticker rows. Before the first verification run, back up all parent/dependent tables and hash complete governance rows (`jsonb_agg(to_jsonb(row) ORDER BY primary_key)`); include artifact tables and metadata pointers because a full suite can pass while appending `backtests`/`research_log` and advancing `strategies.metadata`. If leakage occurs, recover in foreign-key order, require the exact pre-test hash, reopen any falsely completed task, and queue the remaining isolation work. Verify the committed artifact from a clean detached worktree. Prefer a disposable test database long-term, and confirm code under test does not commit or open a separate writer; see `references/live-postgres-test-rollback-isolation.md`.
- **Verify rollback safety after a real guardian tick, not only immediately after writing probation.** Because `cron/jobs.json` mixes declarative job configuration with scheduler runtime state, hash a canonical declarative projection rather than the raw file: ignore top-level `updated_at`, per-job run timestamps/status/errors/claims, transient `scheduled`↔`running` state, and `repeat.completed`, while retaining pause/enabled/schedule/prompt semantics. During active probation, refresh only the manifest's observed hashes and never `latest_snapshot`; assert `manifest.latest_snapshot == probation.snapshot_path` after periodic guardian + cron activity. If it diverges, immediately restore the original snapshot, clear probation, record the rollback, and block identical retry. Regression-test both runtime-only hash stability and rollback-anchor preservation, and compare actual anchor paths rather than snapshot counts because bounded retention can keep counts constant. See `references/guardian-probation-dynamic-cron-churn.md`.

## Workflow

1. Establish baseline health.
   - Run `hermes status --all` to see provider, gateway, platform, and high-level environment status.
   - Run `hermes doctor` for dependency/config/tool availability diagnostics.
   - Run quick direct probes for the items doctor complains about, e.g. `node --version`, `npm --version`, `rg --version`, or a Python import in the Hermes venv.

2. Separate installable dependencies from credential/config gaps.
   - Installable examples: `nodejs`, `npm`, `ripgrep`, optional Python packages such as `python-telegram-bot`.
   - Credential/config examples: API keys, OAuth login, provider-specific tokens, Home Assistant/Spotify/Feishu setup, CDP endpoint configuration.
   - Do not describe unconfigured credentials as broken tools; report them as needing setup.

3. Install OS packages with the system package manager.
   - On Ubuntu/Debian:
     ```bash
     apt-get update
     DEBIAN_FRONTEND=noninteractive apt-get install -y nodejs npm ripgrep
     ```
   - Verify immediately:
     ```bash
     node --version
     npm --version
     rg --version | head -1
     ```

4. Install optional Python packages into the Hermes runtime venv, not an unrelated system Python.
   - Resolve the Hermes venv path from the install; common path:
     `/usr/local/lib/hermes-agent/venv/bin/python`
   - Prefer `uv pip install --python /path/to/venv/bin/python <package>`.
   - If `apt-get install python3-<pkg>` makes `/usr/bin/python3` work but Hermes cron/tools still fail, the missing package is in the wrong Python; install into the Hermes venv and verify with that exact interpreter.
   - Example:
     ```bash
     uv pip install --python /usr/local/lib/hermes-agent/venv/bin/python python-telegram-bot
     /usr/local/lib/hermes-agent/venv/bin/python -c 'import telegram; print(telegram.__version__)'
     ```
   - For HTML parsing dependencies such as `bs4`, see `references/hermes-runtime-optional-python-deps.md`.

5. Let Hermes auto-fix its own command/path issues.
   - Run `hermes doctor --fix` after installing dependencies.
   - This can repair items like a missing `~/.local/bin/hermes` symlink.
   - If `hermes doctor` reports `Skills Hub directory not initialized`, run `hermes skills list` once and then re-run `hermes doctor`; this initializes the hub/lock state without changing installed skills.

6. Apply approval-mode preference when requested.
   - If the user says to stop asking for permissions, allow all permissions, or otherwise asks for YOLO behavior, set the durable config instead of only suggesting a per-command flag:
     ```bash
     hermes config set approvals.mode off
     ```
   - Verify from `~/.hermes/config.yaml`; the CLI may serialize this as boolean `False` rather than the literal string `off`.
   - Restart gateway/platform services so background/gateway sessions pick up the new approval mode:
     ```bash
     hermes gateway restart
     hermes gateway status
     hermes cron status
     ```
   - Tell the user that the current already-running CLI session may still have cached approval behavior until they start a fresh session; restarted gateway/platform sessions should use the updated config.
   - Keep secret redaction separate: disabling approvals/Yolo does not disable redaction and is not a credential-handling approval.

7. Verify with both diagnostics and live smoke tests.
   - Re-run `hermes doctor`.
   - For profile-scoped cron operations, check the profile that owns the jobs explicitly (`hermes --profile <name> cron list --all`). Do not rely only on the active profile: scheduled ops jobs may run from a Mike/admin profile while production jobs live under `default`, `clerky`, or another worker profile. If an ops pre-run/triage script only prints the active profile's empty cron list, fix the script to include the production profile cron listing as deterministic context so future runs do not rediscover or misreport the same issue.
   - For script-only/no-agent watchdogs, empty stdout with exit code 0 is normally a healthy silent run. Report only nonzero exits or actionable output. If an aggregate usage snapshot emits a threshold line but the dedicated usage-limit watchdog runs silently twice and scoped auth is healthy, treat it as a usage-volume warning, not an active quota/rate-limit incident; do not pause jobs unless the watchdog/logs show a real limit event.
   - For LLM cron jobs that should skip the agent based on a deterministic pre-run script, use the scheduler wake-gate convention: make the script's final non-empty stdout line JSON with `{"wakeAgent": false}`. A human-readable line such as `skipped: budget ...` is useful but does not by itself prevent the LLM call; the JSON line is the gate parsed by cron. If a wrapper-only wake-gate change is rolled back by probation/guardian, do not reapply it identically; put the gate in the live context implementation before any task claim, `agent_runs` start, or LLM-context output, then smoke both simulated-block and OK paths. If a probation marker expires exactly at the optimizer's scheduled start and the guardian restores the latest known-good before the optimizer can confirm, do not automatically classify it as a functional regression: first rerun the affected wake-gate/context smoke and check whether the intended `skipped: budget` + final `{"wakeAgent": false, "reason": "budget"}` behavior survived in the restored snapshot. When the budget gate itself is blocked, keep the optimizer plan-only: record task/run/metrics and update the todo/lesson, but make no config/cron/code change. For the cheap guardian/config check in this path, use `config_guardian.py --skip-cli` (or the pinned wrapper); do not use unsupported `--health-only`. For multi-context Wolfy budget gates, use a shared helper where practical, wire every LLM context that can spend tokens (Alpha, EOD report, Sentinel, Yang, weekly research), prove the blocked path emits the final JSON gate, and verify before/after mutation counts for `agent_runs`, `agent_tasks`, and any report tables. See `references/wolfy-jonah-budget-wake-gate-probation-rollback-2026-07-08.md`, `references/wolfy-multi-context-budget-wake-gate-2026-07-08.md`, and `references/wolfy-optimizer-probation-expiry-budget-gate-2026-07-09.md`.
   - When checking cron scheduler health around a just-due run, do not rely on `hermes cron status` alone if it still shows a stale `Next run` timestamp. Cross-check `hermes --profile <name> cron list --all`, cron output/session creation for the specific job ID, and gateway/agent log lines before reporting a stuck scheduler; if a due job is only a minute or two stale, wait/poll once rather than declaring failure. If an LLM-driven cron job is currently running on the cron ticker, just-due no-agent/script jobs may remain listed at their old `Next run` until that active run exits; inspect `agent.log` for the active `cron_<job_id>...` session and only classify the scheduler as stuck if the due jobs remain stale after the active run finishes. If `cron status` remains stale but gateway logs show only heartbeat/memory-monitor lines, also inspect `/root/.hermes/cron/.tick.lock` age and the gateway process/threads before taking action; a zero-byte tick lock with no matching cron session can be a lead, but treat it as unresolved scheduler triage unless it persists past the next poll or blocks jobs. For default-profile Wolfy jobs, check both `/root/.hermes/cron/.tick.lock` and `/root/.hermes/profiles/default/cron/.tick.lock`; the active lock may still live in the global cron directory even when commands are run with `--profile default`. When querying Hermes `state.db` directly for cron session evidence, use the live `sessions` schema (`id`, `source`, `started_at`/`ended_at` REAL unix timestamps); do not assume nonexistent `session_id`, `created_at`, or `updated_at` columns. If Mike's LLM triage overlaps the weekday EOD ingest/signals window and EOD shard jobs advance `Next run` without fresh `Last run`/session evidence, manually smoke the exact shard wrappers, verify Postgres `runs`/`prices` row deltas, and preserve a scheduler wake gate in Mike's triage context that emits final JSON `{"wakeAgent": false, "reason": "eod_ingest_window"}` during 16:25-17:10 America/New_York; see `references/mike-eod-ingest-window-wake-gate-2026-07-21.md`. See `references/wolfy-embedding-and-ad-hoc-query-triage-2026-06-19.md`, `references/wolfy-cron-stale-tick-lock-triage-2026-06-20.md`, `references/wolfy-cron-tick-lock-and-visible-ledger-smoke-2026-06-20.md`, and `references/mike-state-db-cron-session-schema-2026-07-12.md`.
   - For read-only Wolfy visible-progress/status helpers used by several cron/planner probes, prefer tolerant CLI compatibility over brittle one-off invocations: preserve legacy flags, add natural aliases such as `--format markdown|json` and compact-output options such as `--limit N`, keep the helper strictly read-only, restore executable mode when direct invocation is expected, and verify compile + Markdown + JSON + two silent autorepair runs. See `references/wolfy-visible-progress-ledger-cli-compat-2026-06-20.md`.
   - Keep guardian tests isolated from live Wolfy telemetry. Subprocess tests for `config_guardian.py` must not pass the production `wolfy` DSN, because healthy/rollback fixture cases otherwise insert synthetic `gateway_healthy` and `config_rollbacks` rows into live `loop_metrics`. Use a deliberately unavailable test DSN (metric writes are best-effort) or a disposable test database, verify the test suite creates no new live metric rows, and remove only precisely identified synthetic fixture rows if leakage already occurred.
   - Avoid piping live Hermes/cron/log output directly into an interpreter for ad-hoc filtering (for example `hermes ... | python3 - <<'PY'` or `hermes ... | python3 -c ...`): Tirith may block it as pipe-to-interpreter. Use plain CLI output, write to a temp file and inspect it with `grep`, `read_file`, or `search_files`, or add a purpose-built `--json`/`--limit` flag to the helper instead of post-processing through Python. See `references/mike-silent-ops-pipe-filter-and-active-tick-2026-07-07.md`.
   - Do not put psql meta-commands such as `\i` inside `psql -c "..."`; `-c` sends one SQL string and psql will error near `\`. To verify an init file, use `psql -d wolfy -v ON_ERROR_STOP=1 -f /root/.hermes/wolfy/postgres_init.sql` for the idempotent live apply, or write a temporary SQL file containing meta-commands and run `psql -f /tmp/file.sql`. Do not report the `BEGIN; \i ...; ROLLBACK;` failure as schema drift.
   - When manually smoking cron `no-agent` helper scripts, run them with the interpreter implied by the file/shebang (`python3 /root/.hermes/scripts/foo.py` or direct executable invocation), not by wrapping every script in `bash`. A Python helper invoked as `bash foo.py` produces misleading shell parse errors even though cron/shebang execution is healthy; treat that as a smoke-test invocation mistake, then rerun with `python3` before reporting a broken watchdog.
   - For Wolfy script-only intraday scanner snapshots that time out under the cron script limit, prefer a bounded rotating Postgres-only scan over reintroducing retired SQLite fallback: add/verify `--max-symbols` batching in `intraday_scanner_snapshot.py`, ensure `wolfy_scanner.run_scan(..., db_path=None, persist=True)` still calls the Postgres persistence path, keep SQLite only as an explicit test/legacy `--db-path`, and verify with direct silent wrapper smokes, targeted pytest, and fresh `scanner_runs`/`scanner_results` rows. Every rotating batch must include SPY and QQQ even when they fall outside the selected slice; `rank_metrics()` must fail closed when either benchmark metric is absent rather than defaulting benchmark return to zero, which falsely makes each ticker's relative-strength value equal its own 20-day return. Persist the actual attempted-symbol count in `scanner_runs.symbols_scanned`; backfill older zero/null aliases from result counts when needed. If cron still shows the old timeout while an LLM ops tick is active, treat the stale `Last run` as scheduler/tick context until the next tick. For tiny manual smokes using relaxed thresholds such as `--min-ranked 0`, a zero-ranked batch is healthy and should not require `latest_data_date`; keep the normal cron threshold strict, but let the relaxed smoke exit 0 silently when no ranked rows exist, and add a regression test for that case. See `references/wolfy-intraday-scanner-bounded-postgres-snapshot-2026-07-10.md` and `references/wolfy-intraday-scanner-zero-ranked-smoke-2026-07-10.md`.
   - For Postgres no-agent helpers that update rows via `psycopg`, explicitly `conn.commit()` before exit and verify persistence with a follow-up `psql` query plus a second silent run. Do not trust a `RETURNING` printout alone; uncommitted subprocess updates can look successful while leaving rows unchanged.
   - For Postgres-backed coordination ledgers, watch for context generators that repeatedly re-select stale local `in_progress` work and create duplicate `blocked`/`duplicate-or-already-claimed` `agent_runs`. The safe fix is usually to have context generators claim only fresh queued work, leave stale `in_progress` cleanup to the watchdog, and verify with a post-fix query such as `count(*) where error_message='duplicate-or-already-claimed' and started_at > <fix time>`.
   - For Wolfy EOD `runs` ad-hoc query drift, if probes expect `runs.source` but canonical source detail lives under `runs.detail->>'source'`, add a non-destructive nullable `source` alias, backfill it from JSON detail, update `wolfy_sync_runs_aliases()` to mirror future rows, and preserve the repair in `postgres_init.sql`, `eod_price_features.py`, and canonical/profile `mike_safe_autorepair.py`. Also verify `eod_feature_runs` uses `job LIKE 'eod%' OR job LIKE 'feature%'`; the older `eod-%` filter misses underscore-style canonical jobs such as `eod_price_ingest` and `eod_feature_compute`. If probes expect `runs.ended_at`, mirror it non-destructively from `completed_at`/`finished`, expose it through `eod_feature_runs`, and preserve the alias in `postgres_init.sql` plus canonical/profile autorepair. Verify with the exact failing `runs where source ilike ...` or `select ... ended_at ...` query, an `eod_feature_runs` row count, `postgres_init.sql` with `ON_ERROR_STOP`, autorepair twice for silence, and compile of all wrapper copies. See `references/wolfy-runs-source-alias-and-eod-feature-view-2026-07-20.md` and `references/wolfy-runs-ended-at-alias-and-massive-shard-smoke-2026-07-21.md`.
   - For Wolfy ops/status metric alias drift, prefer compatibility aliases over changing watchdog write paths. If probes expect `system_metrics.metric_name`, `metric_value`, `category`, or `created_at`, mirror canonical storage-watchdog fields (`root_used_pct`, `captured_at`) with nullable columns, backfill existing rows, add a trigger for future rows, and preserve the repair in both `postgres_init.sql` and canonical/profile `mike_safe_autorepair.py`. If budget/guardian/optimizer probes expect `loop_metrics.created_at`, `metric_name`, or `value_numeric`, mirror canonical `captured_at`, `metric_key`, and `metric_value` with nullable aliases plus a trigger, and preserve the repair in `budget_gate.py`, `config_guardian.py`, and `postgres_init.sql`; verify the exact `value_numeric` query, simulated budget OK path, guardian `--skip-cli`, and config-guardian pytest. If `alpha_search_leads` expects `sqlite_id` but canonical `alpha_leads` has `legacy_id`, expose both in the compatibility view (`legacy_id`, `legacy_id AS sqlite_id`) rather than adding a mutable duplicate column. Verify `postgres_init.sql` with `ON_ERROR_STOP`, run autorepair twice for silence, run the storage watchdog once, and query both alias surfaces. See `references/wolfy-system-metrics-and-alpha-search-alias-preservation-2026-07-11.md` and `references/wolfy-loop-metrics-compatibility-aliases-2026-07-15.md`.
   - For Wolfy tiered Massive history backfills, distinguish true missing-history targets from current-but-naturally-short tickers. If a ticker has `< DEPTH_READY_BARS` bars but `latest_dt` is current, do not keep reselecting/refetching it every bounded cron run; select no-price tickers immediately and partial-history tickers only when stale (for example `latest_dt < current_date - interval '5 days'`). Keep the cron wrapper bounded below the script timeout with small `max-batches`, then verify the runner advances to new tickers and exits 0. For multi-batch bounded runs, also prevent duplicate ticker selection within the same run by keeping an in-run attempted/exclusion set; otherwise a still-missing or naturally short ticker can consume both scarce batches before the next cron tick. For operations status SQL, do **not** assume `universe_backfill_targets.latest_dt` or `universe_backfill_targets.loaded_bars` exists; derive latest coverage and bar counts from `prices` and join them to `universe_backfill_targets` by `symbol`. If a just-due bounded backfill is delayed by an active LLM cron tick, it is safe to manually run the bounded wrapper as a smoke/advance step and report concrete ticker/count deltas instead of declaring scheduler failure. To close a backlog rather than merely advance it, use one threshold consistently, account for every target as depth-ready/current-short/recorded-unavailable/eligible, require feature-date parity, record repeated provider-limited histories without deactivating incremental ingestion, and prove a zero-batch rerun. See `references/tiered-backfill-completion-and-provider-limited-targets.md`, `references/wolfy-tiered-backfill-current-short-history-skip-2026-07-02.md`, `references/wolfy-tiered-backfill-coverage-query-and-active-tick-2026-07-09.md`, and `references/wolfy-tiered-backfill-in-run-exclusion-2026-07-23.md`.
   - If an LLM-driven cron job times out before it can finish its Postgres `agent_runs` row, close only the stale run row as `blocked` with `records_created=0` and a specific timeout/config summary; do not fabricate the missed report or mark it completed. Before changing models, inspect the current cron job config because the historical `last_error` may mention startup/default model text that differs from the saved per-job fallback. If the job already has a per-job fallback model (for example `model: gpt-5.4`) but the saved `last_error` still names the default model (`gpt-5.5`), treat the error text as stale/contradictory until verified: inspect `cron/jobs.json` or `hermes --profile <name> cron list --all`, then run a direct one-shot smoke with that exact profile/model (for example `hermes --profile default chat -Q -m gpt-5.4 -q 'Runtime smoke: reply with exactly OK.'`). Do not change cron models or alert the user if the context smoke, model smoke, watchdogs, and coordination ledger are healthy. Verify `stale_started_runs=0`, rerun script-only smokes/autorepair, and report the next scheduled retry separately from the closed DB run. When compiling cron/helper scripts during this triage, resolve and compile the exact invocation layer instead of assuming the script lives under `/root/.hermes/wolfy/`; some cron wrappers are global-only under `/root/.hermes/scripts/`, while ledger helpers may be Wolfy-local. For Jonah-style task claims left open by a transient usage-limit/startup failure before any artifact was created, close the stale `agent_runs` rows as `blocked` with `records_created=0` and requeue the linked `agent_tasks` for retry rather than marking the research completed or fabricating output; then run the usage-limit watchdog twice, stale cleanup, embedding sync, and coordination-count verification. ## Messaging attachment smoke test

Use this pattern when the user asks whether Hermes can “drop a file” into a gateway channel:

```text

send_message(target='discord:<channel_id-or-home>', message='Test upload\n\nMEDIA:/tmp/hermes-<platform>-file-test.txt')
```

Verification is the `send_message` result, not just the absence of an exception. Capture and report `platform`, `chat_id`, and `message_id` when present. Treat credential/channel permission errors as setup issues; do not encode them as durable tool failures.

## Reporting conventions

- Keep the result concise and grouped as: installed, fixed, verified, remaining.
- Distinguish “remaining because credentials/config are missing” from “remaining because system dependencies are missing.”
- Avoid persistent negative claims like “browser is broken.” Say what setup is missing or what smoke test now confirms.
