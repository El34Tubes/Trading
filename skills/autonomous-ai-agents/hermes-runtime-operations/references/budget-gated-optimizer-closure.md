# Budget-gated optimizer closure

Use this checklist when a deterministic budget gate blocks an autonomous optimizer before implementation.

## Rule

`BUDGET=block` is a hard PLAN-ONLY boundary. Do not edit code, config, cron, migrations, schedules, or orchestration. Allowed work is deterministic orientation, review, durable task/run/KPI state, a narrowly staged ledger note, and reporting.

## Closure sequence

1. Capture the gate output and expected nonzero exit. Preserve the script status explicitly: a trailing diagnostic such as `printf` makes the shell command itself exit 0 even when the gate exited 1. Use `set +e; output=$(... 2>&1); rc=$?; set -e`, print both, and assert `rc != 0` with `output` beginning `BUDGET=block`. **Run this decision-critical probe in a small dedicated tool call, not inside a giant orientation command with full Git status, process listings, cron output, or the visible ledger.** Large combined output can be truncated and hide the gate line/exit status, forcing an avoidable repeat and weakening the audit trail. **If more verification commands follow in the same shell invocation, do not use `exit 0` in the successful `case` arm**—that terminates the shell and silently skips guardian/config checks while returning success. Use `case "$output" in BUDGET=block*) : ;; *) exit 2 ;; esac`, or isolate the gate assertion in its own command. Run guardian health with the production home pinned, parse config and cron JSON/YAML, verify cron list and gateway, check probation, run the deterministic progress ledger, and stay outside active market/data windows.
2. Verify the prior task's claimed commit and Definition of Done before creating current state. Do not trust the newest `optimization_todo.md` heading alone: the ledger can lag a successful run. Reconcile the current Git `HEAD`, its commit scope, the matching completed `agent_tasks` row, and the latest terminal `agent_runs` row; then rerun the named focused and broad tests from that task's stored DoD. Prefer resolving the prior task by the exact `HEAD` commit hash or known task ID/fingerprint. If using a task-type filter, include plan-only types such as `optimization_plan_only`; a narrow `IN ('optimization','self_optimization')` filter can omit the actual latest closure and make an older task look current.
   - `HEAD` can legitimately correspond to the last completed closure while a newer implementation attempt is terminal `failed`/`blocked`, fully recovered, and has no commit. Review both facts independently: verify the committed closure against `HEAD`, then verify the newer failed run's recovery evidence and that its task is no longer actively claimed. Do not manufacture a missing commit for a correctly reverted attempt or mistake the older `HEAD` for stale lifecycle state.
   - If that recovered attempt left a durable, uncommitted ledger note, the next plan-only ledger commit may intentionally include both that prior note and the current note. Declare this in the current task's DoD before staging, inspect the combined diff, and record the inclusion in verification metadata so the extra insertion count is auditable rather than mistaken for swept-up work.
3. Create and claim a dedicated plan-only `agent_task`; write a machine-checkable `definition_of_done`; start an `agent_run` linked to that task.
   - `wolfy_agent_cli.py task-ensure` does not currently accept `definition_of_done`, so create the task with the CLI, then update that field before claiming it.
   - Parse the CLI's exact output key `AGENT_TASK_ID=<id>`. Do not search loosely for `TASK_ID=`: it may happen to match as a substring today, but it is brittle if output gains another task-ID field. Assert the extracted value is numeric and read the row back by fingerprint before continuing.
   - Under `set -e`, avoid a parser like `while read k v; do [ "$k" = AGENT_TASK_ID ] && printf ...; done` inside command substitution: later nonmatching lines can leave the loop/substitution with status 1 and abort the shell after the task was already created. Use a total parser whose nonmatches succeed, for example `case "$k" in AGENT_TASK_ID) printf '%s' "$v" ;; *) : ;; esac`, then validate the numeric ID. If parsing still fails, resolve the existing task by its unique `source_fingerprint`; update its DoD and continue instead of creating a duplicate.
   - Prefer a parameterized `psycopg` update for long DoD/verification text. Do not rely on `psql -v name=... -c "... :'name' ..."`: variable interpolation can be disabled or behave differently in `-c` invocations, leaving the task created but its DoD unset. Assert `cursor.rowcount == 1`, then read back `status` and `definition_of_done IS NOT NULL`.
   - Because task creation and DoD update are separate operations, a failed update is recoverable: leave the queued task in place, correct the parameterized update, verify it, and only then claim/start the run. Re-resolve the existing row by `source_fingerprint`; do not create a duplicate task after a transient SQL invocation mistake.
   - Treat `status`, `claim_token`, and `claimed_at` together as claim evidence, but let terminal status control whether work is active. Compatibility aliases such as `claimed_by` can remain populated from historical assignment metadata even after a task is requeued; a row with `status='queued'`, null `claim_token`, and null `claimed_at` is not actively claimed merely because `claimed_by` is non-null. Likewise, a terminal `blocked`/`completed` task may retain its historical `claim_token` and `claimed_at`; verify its linked run is terminal and describe it as **not actively claimed**, rather than inaccurately saying the claim fields are empty or that it was never claimed. Use this distinction when asserting that deferred implementation work remained untouched.
4. Inspect the live Postgres schema before writing task metadata **or KPI queries**. Compatibility columns vary; for example, `loop_metrics` may use `metric_key`/`metric_value`/`captured_at` with aliases `metric_name`/`value_numeric`/`created_at`, and may have no `metadata`, `recorded_at`, or `ts` column. Query `\d loop_metrics` first and use the live timestamp/key columns. Likewise, the task blocker field may be `blocker_reason`, not `blocked_reason`. Do not guess column names from old scripts or prior sessions. **Make schema discovery a separate call from the dependent query**: batching `\d table` and a guessed `SELECT` into one `psql` invocation prints the schema but cannot retroactively repair the already-constructed query, so stale columns still abort the batch. Read the schema output, then construct and run the query in the next call.
5. Record every required `loop_metrics` row against the current run ID **before** completing either row. Build the metric set, insert it, and assert exact total/distinct-key/provenance counts inside one database transaction; if a scratch Python or SQL query fails before commit, confirm the transaction rolled back (current-run metric count is still zero), correct the query, and retry without deleting or duplicating rows. Verify the exact metric count and keys. If one exploratory KPI query fails because an assumed alias is absent, correct it from the live schema and rerun; do not treat a resolved read-only query mistake as a run failure or persist the stale assumption. At `run-finish`, set `records_created` to the verified number of durable metric rows created by this closure (normally the required KPI count, currently 25), not a guessed zero; read it back with the terminal run row.
6. Add only the durable plan-only note to the operational ledger. In a dirty live-state repository, stage the exact path and assert `git diff --cached --name-only` contains only that file before committing.
   - Inspect the index **before** staging. Never use `git reset` merely to obtain an empty index unless you have proved the index was already empty; it can silently unstage another worker's reviewed changes. If unrelated staged work exists, preserve it and use a temporary index (`GIT_INDEX_FILE`) or construct/apply an exact patch without disturbing existing entries. Re-read the original index and verify the final commit scope afterward.
   - Path-only scope is not enough when the ledger already has legitimate uncommitted notes from a prior run. Inspect `git diff -- <ledger>` before staging. Either deliberately include the prior durable note and state that the commit contains both ledger entries, or stage only the current hunk with an exact patch/temporary index. Never silently sweep unknown same-file edits into the accounting commit; verify the final insertion count and committed diff.
7. After the commit exists, store the real full commit hash, verification result, and verification timestamp on the task; read those fields back and require an exact hash match. Only then complete the task and finish the run. Lifecycle helpers may update summaries/status independently of verification metadata, so do not assume `task-complete` proves the artifact was attached. If the task/run was accidentally terminalized first, treat that as recoverable ledger ordering—not a reason to create a replacement task or duplicate metrics: immediately write and read back the missing commit/verification fields, re-run `git show --check`, reassert the linked run's exact KPI count, and record the ordering mistake in the durable lesson before reporting success.
8. Query both rows to confirm terminal status and verify no stale `started` optimizer run remains. Distinguish the task-linked plan-only run from any scheduler-owned outer cron usage-sync row: the inner run must be terminal before reporting. A fresh outer row for `job_id='cron:<current_job_id>'` may remain `started` until the conversation exits, but some scheduler paths do not create or expose that row during the inner closure. Do not require an outer row to exist. If one is present, exclude only that exact fresh current cron row by job ID/session identity and age; do not exclude the just-finished inner run ID and then misclassify another row as stale. Any older started row beyond the expected run window still requires explicit cleanup.
9. Report the commit as local/unpushed and retain the queued implementation task for a future run with sufficient headroom.

## Metric derivation pitfalls

- Use `budget_gate.py --no-record` for **every** orientation and verification probe, including the first cheap Phase-0 check. The default invocation writes `tokens_today` and `usage_headroom_pct` without the current optimizer `run_id`, creating orphan KPI rows before the task/run exists. Do not run the default form first and then “correct” it with `--no-record`; the first probe has already mutated telemetry.
- Preserve an expected blocked exit explicitly (`set +e; out=$(...); rc=$?; set -e`) and assert both `rc != 0` and `out` starts with `BUDGET=block`.
- A low-headroom block line may report only `low_headroom_pct` and omit `tokens_today`. Derive the token count separately with the same New York day-boundary query used by `budget_gate.py` (`SUM(input_tokens + output_tokens)` from `agent_runs` since local midnight). Determine which source caused the block: provider/auth headroom and local token-cap headroom are independent. If provider headroom is the limiter, record the emitted percentage as `usage_headroom_pct` and the fresh Postgres sum as `tokens_today`; do **not** require the token formula to reconcile to provider headroom or claim that it does.
- Treat the gate output as the decision-time snapshot, not necessarily the final KPI snapshot. Another tokenized cron session may finish while the plan-only optimizer is recording state. Recompute `tokens_today` immediately before inserting metrics, preserve the gate's limiting provider percentage when that caused the decision, and record each measurement's source/time in provenance. The implementation stop remains binding even if a later snapshot happens to recover.
- After a rolled-back orchestration change, never copy the latest historical KPI as current state: a pre-rollback metric can still say `max_turns=30` while live `config.yaml` has correctly returned to `90`. Parse the live config for current-state KPIs, retain the failed task/run as historical evidence, and note the rollback provenance. Apply the same rule to cadence, parallelism, and enabled-job counts.
- `cron/jobs.json` is not guaranteed to have one historical shape. Validation helpers should accept either a top-level list or an object containing `jobs` before iterating job dictionaries; assert the resolved value is a list and then verify optimizer/guardian IDs and enabled flags. Do not let a shape-assumption traceback invalidate the already successful budget/guardian probes—fix and rerun the parse check before closure.
- For `llm_calls_per_day`, do not count every `agent_runs` row: one logical cron invocation can create a tokenless context/work row plus a tokenized cron session-sync row. Count completed tokenized cron session rows (or distinct cron session IDs) and state whether the currently-running optimizer is excluded; otherwise the KPI can double-count agent work.
- Do not assume the gate's `tokens_today` equals the sum over only terminal rows. The scheduler-owned outer cron usage-sync row can still have `status='started'` while already carrying a live `total_tokens` value, and the canonical budget gate may include that value. Preserve the gate's exact decision-time token total as the audited `tokens_today` value; if you also query completed tokenized rows for `llm_calls_per_day`, record the different scope explicitly rather than forcing the two measurements to reconcile.
- For latest-date coverage, compute the maximum date in a CTE and join/filter rows to that date before counting tickers. A query that selects `max(dt), count(distinct ticker)` in one aggregate counts tickers across the whole table, not only the latest date.
- A KPI named `freshness_core_pct` must use the declared core/tier-1/2 universe denominator—not every active symbol, broad research symbol, or `unassigned` row. Import/read the canonical project constant (currently `orchestration_config.CORE_EOD_UNIVERSE`) instead of hand-copying a remembered ticker list; stale hardcoded members can fail assertions or silently measure the wrong universe. Assert every canonical ticker has price history. For delayed EOD pipelines, use the latest **common complete core date** (the minimum of each core ticker's latest date), then count core coverage at that date; a few newer bars from another path must not make an otherwise complete delayed session appear mostly stale. Record the exact date and numerator/denominator in `notes`. If the canonical scope cannot be reconstructed, carry forward the last verified value with provenance rather than measuring a different scope under the same key.
- Keep coverage completeness and calendar lag as separate facts. Weekends, exchange holidays, and delayed-data policy can increase `freshness_lag_days_max` while `freshness_core_pct` remains 100% for the latest expected completed session. Record both with the common session date, and do not report a pipeline regression from calendar-day lag alone.
- Derive depth readiness from the canonical project threshold (currently `orchestration_config.DEPTH_READY_BARS=495`), not a copied rounded label such as “500 bars.” Record numerator, denominator, and threshold in metric notes.
- Do not silently recompute inventory KPIs with a broader search definition. If `legacy_db_refs_live`, `duplicate_script_twins`, or a freshness denominator comes from a previously verified inventory and no equivalent inventory pass ran, carry it forward with an explicit note rather than presenting it as freshly measured. Never substitute a superficially similar universe table whose scope differs.
- Compute tracked repository size in one process. Avoid `git ls-files -z | xargs -0 du -cb | tail -1`: when the file list exceeds the platform's argument limit, `xargs` invokes `du` in batches and `tail -1` reports only the final batch, silently undercounting the repository. A robust probe is Python over `git ls-files -z`, summing `Path.stat().st_size` for each existing tracked path, then dividing by 1,048,576; include the byte numerator in the metric note.
- Give every KPI row auditable provenance in `notes`: use `measured:<command/query or deterministic source>` for values derived this run, and `carried_forward:<prior run_id>; reason=<why not remeasured>` for unchanged inventory values. A generic note such as “plan-only optimizer iteration” is insufficient because it makes copied values look current. Before closure, sample or query all current-run metrics and reject rows whose notes do not identify measured versus carried-forward provenance.
- Frequent no-agent loaders/backfills can change freshness counts while the optimizer is open. Compute each freshness KPI in one SQL statement/transaction, persist the exact numerator, denominator, threshold/date, and query provenance in its note, and verify the stored row. Do not mix a numerator from an earlier visible-ledger snapshot with a denominator from a later query or treat a legitimate concurrent increase as a regression.
- Staged secret-scan stdout itself can be redacted when it contains credential-like words, even for an innocuous numeric result such as `...HITS=0`. Make the scanner's exit status authoritative: exit nonzero on any hit, require exit zero before commit, and record that verified status. Do not infer failure from a redacted display or claim zero hits if the command did not enforce the assertion.
- When checking recent cron failures, do not broadly regex-search every rendered cron output for words such as `error`, `failed`, `429`, or `usage limit`. Agent outputs may embed loaded skill text, prompts, documentation, or quoted troubleshooting examples containing those words, producing large false-positive sets. First use scheduler/job metadata (`last_status`, `last_error`, delivery error, recent terminal `agent_runs`) to identify suspect runs; then inspect only the result-bearing portion of those specific outputs. Treat prompt/skill echoes as context, not failure evidence.
- When inspecting recent `agent_runs`, query the live schema first and use canonical fields such as `ended_at` and `error_message`; a stale diagnostic that assumes `finished_at`/`error` can abort a multi-command `psql` probe after earlier statements already printed. Treat earlier successful read-only output as partial orientation evidence, fix the query, and rerun the failed probe before closure.
- Keep stale-run and stale-task checks as separate queries, or fully qualify every shared column (`agent_runs.status`, `agent_tasks.status`). Do not manufacture a combined result with a cross join or lateral placeholder that exposes two columns named `status`: an unqualified filtered aggregate then fails as ambiguous after other useful orientation output has already printed. Correct the read-only query and rerun it; this is not a run failure.
- Scope the Phase-0 process probe to relevant Hermes, cron, guardian, Postgres, and worker processes rather than dumping the host's complete process table. A full `ps -eo ... --sort=-etimes` on a long-lived host can bury actionable evidence in kernel threads and risk output truncation; use a deterministic filtered probe while ensuring the filter command itself does not hide a nonzero status.
- When writing ad-hoc psycopg SQL, remember psycopg parses every `%` in the query string as placeholder syntax. Bind wildcard patterns (`... ILIKE %s`, parameter `'%recurring%'`) or escape literal percent signs as `%%`; embedding `ILIKE '%recurring%'` directly can raise `ProgrammingError: only '%s', '%b', '%t' are allowed as placeholders`. Prefer binding because it is clearer and avoids accidental placeholder parsing.
- In psycopg 3, bulk execution belongs on a cursor: `with conn.cursor() as cur: cur.executemany(sql, rows)`. `Connection.executemany(...)` is not available. Keep the insert and exact row-count assertions inside the same transaction; if the wrong API raises before commit, verify the current-run metric count is still zero, fix the cursor call, and retry idempotently.
- PostgreSQL polymorphic JSON constructors may not infer types for bound parameters. A statement such as `jsonb_build_object('commit_hash', %s, 'verification_result', %s)` can fail with `IndeterminateDatatype`. Cast values explicitly (`%s::text`) or serialize one dictionary client-side and merge it as `%s::jsonb`. Keep task verification update separate from task/run completion; if the metadata update fails after the local commit, repair and read it back before terminalizing either row.
- Resolve the project's database adapter API before writing a temporary metrics/DoD script; do not guess exported helper names from the filename. For the current Wolfy adapter, use `from wolfy_db import connect_postgres` (or inspect `wolfy_db.py` first), not an assumed `postgres_dsn` export. A failed DoD update is recoverable: verify the task stayed queued, reuse its fingerprint/ID, and continue without creating a duplicate.
- Prefer a temporary Python file for multi-step task/KPI writes. If an inline shell heredoc is unavoidable, put the terminator on its own line and do not append claim/completion commands until after it; a missing terminator can feed shell commands to Python and leave lifecycle state half-created. Keep DB update, claim/start, metric insertion, and completion as separately verified steps.
- Rerun the prior task's named test targets and judge the current result, not a historical suite-count literal. Resolve each stored test path before execution (search the repository when the DoD names a target imprecisely), and run the verification shell with `set -euo pipefail` or explicit status assertions. Otherwise a missing pytest path can return exit 4 while later successful commands make the overall shell exit 0, falsely presenting the review as passed. **Use the project's actual test runner. A pytest-style module invoked through `python -m unittest ...` can report `Ran 0 tests` and exit 0; that is not a pass. Run `python -m pytest <resolved-path>`, retain the collection/result line, and assert the collected count is nonzero whenever the DoD names tests.** Test discovery can legitimately move from (for example) 196 to 191 tests as unrelated work changes; a zero-exit full suite plus the expected focused tests is the regression signal unless the DoD explicitly requires a fixed inventory count. Record the current count rather than copying yesterday's number.
- After inserting metrics, assert both total row count and distinct metric-key count for the current `run_id` before completing the task or run.
- Keep final Git verification free of truncating pipelines under `set -o pipefail`. Commands such as `git status --short --branch | head -1` can make Git receive SIGPIPE and return 141 after printing the desired line, falsely turning an otherwise valid verification block red. Prefer bounded native commands (`git rev-list --count origin/main..HEAD`, `git rev-parse HEAD`, `git diff --cached --name-only`) or capture output and summarize it outside the fail-fast block. If a SIGPIPE-only probe fails after earlier assertions passed, rerun the probe without the truncating pipe; do not misclassify the artifact as failed or duplicate task/KPI state.
- KPI compatibility mirrors are not necessarily the canonical source. Inspect the live table before deriving each metric and prefer typed top-level columns over similarly named JSON compatibility keys. For example, strategy OOS completion is measured from `strategies.latest_oos_verdict IS NOT NULL`; `strategies.metadata->>'latest_oos_verdict'` may be absent even when the canonical boolean is populated. Read back every newly inserted metric, sanity-check it against the prior run, and correct any bad current-run row before task/run completion rather than preserving a known-wrong value for count consistency.
- Do not probe guessed guardian flags with a fallback chain such as `config_guardian.py --check || config_guardian.py`: the unsupported first invocation creates avoidable error noise. Use the documented production-home command directly: `config_guardian.py --home /root/.hermes --skip-cli` for the cheap plan-only check, and run the normal command only when full CLI health checks are intentionally required.

## Verification minimum

- Budget gate emitted `BUDGET=block` and nonzero exit, using `--no-record` for probes.
- Guardian healthy; config/cron parse; optimizer and guardian enabled; gateway healthy.
- No probation marker requiring resolution.
- Progress ledger and prerequisite guards pass.
- Required KPI count and distinct-key count are exact for the current run.
- Staged scope is one durable ledger file.
- Task has real `commit_hash`, `verification_result`, and `verified_at`.
- Task and run are terminal; no implementation/config/cron/migration mutation occurred.

## Reporting

Keep the final report short: `CHANGED`, `VERIFIED`, notable `KPI/STATE`, Tier-B `BLOCKED/HUMAN ASK` only when present, and `NEXT ACTION`. State explicitly that the budget gate caused plan-only behavior and that the commit was not pushed.
